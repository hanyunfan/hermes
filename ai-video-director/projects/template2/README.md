# template2/ — multi-character + ref2v + previous-shot chain

This template bakes in everything we learned running a 38-shot project
end to end (new_grok_story, October 2026). Use it as the starting
point for any new story that needs:

* **2+ characters per shot** with **face-consistent** output across the
  whole video
* **Continuous motion** from one shot to the next (no abrupt cut when
  a character is mid-action and the camera changes)

## What's in the box

```
template2/
├── project.yaml               # metadata + status
├── workflow.yaml              # WorkflowMapping: image slots, video slots, frame count
├── story.yaml                 # placeholder story (replace with your own)
├── characters/                # 2 example character cards
│   ├── multi_character_a.yaml # 4 refs: face / hero / side / costume
│   └── multi_character_b.yaml # minimal example (1 ref)
├── imports/
│   ├── references/<char>/     # drop your ref images here
│   └── shots.json             # generated by `video-director build`; you edit raw shots.json before build
├── private/
│   ├── video_workflow_api_r2v.json   # 23 nodes, real, ready to run
│   └── video_workflow_r2v_ui.json    # same in ComfyUI's UI format
├── output/                    # final mp4s land here
└── state/                     # job records + per-shot status
```

## The two key features

### 1. Multi-image character reference (face / hero / side / costume)

Each character card's `reference_images` list can carry several
images, each tagged with `image_type`. The runner sorts them by
priority and routes them into the right `ref_image_<i>` slot of
`MiniMaxH3ReferenceToVideo`:

| image_type  | priority | typical use            |
|-------------|----------|------------------------|
| face        | 0        | tight portrait, identity anchor |
| expression  | 1        | smile / surprise / etc  |
| front/hero  | 2        | full body, default look |
| full        | 3        | costume + body in frame |
| side        | 4        | side profile, helps unet avoid frontal bias |
| back        | 5        | back-of-head, for turnaround |
| costume     | 6        | wardrobe reference     |

The current workflow ships **3 LoadImage nodes** (ref_image_0/1/2),
so up to 3 references per shot will be wired in. The runner warns
and stops at the first missing slot if a project demands more.

### 2. Previous-shot video chain (`ref_videos_0`)

For visual continuity, the framework uploads the **previous shot's
entire mp4** to ComfyUI and wires it into
`MiniMaxH3ReferenceToVideo`'s `ref_videos.ref_video_0` input.
ComfyUI's `LoadImage` decodes the mp4 to a 24-fps IMAGE batch via
pyav; the H3 node encodes it through the VAE and hands the latent
to the unet as a motion anchor. The result: shot N+1 opens matching
the position/expression of shot N's last frame, with a continuous
5-15 second tail rather than a hard cut.

To enable, declare the slot in your `workflow.yaml`:

```yaml
reference_video_nodes:
  ref_video_0: Load Video Ref (previous shot)
```

For shot 1 (no previous shot), the runner leaves the workflow's
default image slot pointing at a 1-second black placeholder, which
is uploaded to `/home/frank/ComfyUI/input/placeholder_prev_shot.mp4`
at framework setup. You can regenerate that placeholder with:

```bash
ffmpeg -y -f lavfi -i color=c=black:s=320x240:r=24:d=1 \
  -pix_fmt yuv420p -c:v libx264 \
  /home/frank/ComfyUI/input/placeholder_prev_shot.mp4
```

## Operational rules (learned the hard way)

These are mandatory if you want a clean 30+ shot run.

### Rule 1: commit your raw story data BEFORE running the build

`video-director build` rewrites every shot yaml in `shots/`, and
some other code paths can also touch `characters/*.yaml`. If you
have uncommitted story edits when build runs, you'll lose them.
Always:

```bash
git add imports/shots.json characters/*.yaml
git commit -m "story: <your change>"
```

…then run build.

### Rule 2: never run more than ~10 shots without a VRAM-clear

ComfyUI's unet/CLIP caches fragment across successive shots and
**render time climbs monotonically** even on a 32 GB GPU. We
measured:

| Shot #  | Render time |
|---------|-------------|
| 1-2     | 14 min (cold start) |
| 3-6     | 24-30 min     |
| 7-10    | 30-39 min     |
| 11+     | often hangs or OOMs |

The framework now calls `/free` (`unload_models: true,
free_memory: true`) **only on the retry path** — when a shot fails
and the runner is about to re-submit. Healthy shots do NOT pay
the reload cost, because `/free` forces ComfyUI to unload the
unet/CLIP/VAE from VRAM and the next prompt re-loads + re-warms
them (30-90 s of fixed overhead per shot). For a healthy 30-shot
run, that's 15-45 minutes of unnecessary reload cost.

If you run the workflow through the ComfyUI frontend instead of
through the framework, hit the **"Unload Models"** button between
shots OR after any failure. For long runs you may also want to
**restart ComfyUI every 20 shots** to fully clear its Python-side
caches.

### Rule 3: poll timeout ≥ 90 minutes per shot

`ComfyUIConfig.poll_timeout_sec` defaults to 90 minutes (was 30
before the fix; 30 was not enough once VRAM fragmented). Don't
lower it back. If you need a hard wall-clock cap, set it on the
config object passed to `ComfyUIGenerator`, never on the global
default.

### Rule 4: the framework does NOT retry on poll success

When `poll()` returns successfully, the shot is committed to
`output/clips/<shot_id>.mp4` and the run moves on. If you see a
shot's mp4 in `/home/frank/ComfyUI/output/video/MiniMax_H3_R2V_*.mp4`
but **not** in your project's `output/clips/`, the framework
abandoned that shot mid-poll — usually because of a VRAM-driven
hang. Check `state/jobs/<shot_id>.json` for the `error_message`
field. Two patterns to look for:

* "did not complete within timeout" → poll ran out of budget. The
  shot may have actually finished in ComfyUI. Manually copy the
  mp4 from `ComfyUI/output/video/` into your `output/clips/` and
  re-run with `--force-regenerate=false` so the framework skips it.
* "execution_error" → ComfyUI raised an error during the run;
  check the corresponding `/history/<prompt_id>` entry for details.

### Rule 5: shot N's first frame is the previous shot's chain

By convention (set in `imports/shots.json`):

```json
{
  "shot_id": "scene_001_shot_002",
  "start_frame_source": "previous_shot",
  "previous_shot": "scene_001_shot_001"
}
```

`video-director build` will write this into the per-shot yaml
automatically from the `previous_shot` field. **Do not** also set
`start_frame: "<some path>"` — that overrides the chain with a
literal image, which is what created the original
"validation shot" bug we hit in the new_grok_story run (shot 2
had `start_frame: imports/references/combined/hero.jpg` left over
from when shot 1 was being used as a one-off test).

Shot 1 should look like:

```json
{
  "shot_id": "scene_001_shot_001",
  "start_frame_source": "manual",
  "start_frame": "",
  "previous_shot": ""
}
```

Shot 2+ should look like:

```json
{
  "shot_id": "scene_001_shot_002",
  "start_frame_source": "previous_shot",
  "start_frame": "",
  "previous_shot": "scene_001_shot_001"
}
```

If you need a hard "reset" mid-story (e.g. a chapter break), set
`start_frame_source: "manual"` and provide a `start_frame` image
path, then resume the chain on the next shot.

## Models required

All paths under `/home/frank/ComfyUI/models/`:

| Type             | Filename                                                |
|------------------|---------------------------------------------------------|
| diffusion_models | `minimax_h3_fl2va_pruned_int8_convrot.safetensors`      |
| text_encoders    | `qwen3vl_32b_heretic_minimax_h3_nvfp4.safetensors`      |
| vae              | `minimax_h3_video_vae_fp16.safetensors`                 |
| vae              | `minimax_h3_audio_vae_fp32.safetensors`                 |
| loras (optional) | `minimax_h3_fl2v_turbo_8step_v1.0_comfyui_bf16.safetensors` |

Note: the unet is `fl2va`, not `ref2va`. Both share the same
`PackedLayout` code path so the H3 reference-to-video conditioning
works. The model's `minimax_refs` input is what `MiniMaxH3ReferenceToVideo`
feeds, regardless of which "va" variant the unet is.

## How to start a new project from this template

```bash
# 1. Copy template2 to your project dir
cp -r projects/template2 projects/my_story
cd projects/my_story

# 2. Edit project.yaml (title, description, language)
# 3. Replace characters/ with your own (keep image_type values!)
# 4. Drop reference images into imports/references/<char_id>/
# 5. Edit imports/shots.json with your 38 shots
# 6. Edit story.yaml (optional — only used for QA, not generation)
# 7. Build + validate + generate
video-director build my_story
video-director validate-imports my_story
video-director generate my_story --backend comfyui --max-retries 2
```

## When NOT to use this template

* You only have **one character** per shot, or you don't care
  about face consistency. Use `template/` instead — it's faster.
* You're generating a single isolated shot (no chain). Use
  `template/` — ref_videos_0 has nothing to chain from.
* Your story is short (< 10 shots) and you don't need VRAM
  cleanup. Either template works; the 90-min poll budget is
  the only practical difference.
